# Library test suite

Everything runs with one command, without a Jenkins instance:

```bash
bash test/run-all.sh
```

The first run downloads the tools into `${DEVSECOPS_TOOLS:-$HOME/.cache/devsecops-library-tools}`: JDK 21, Groovy 2.4.21, the Jenkins 2.479.3 libraries and the `script-security` plugin (the same versions the customer runs). Later runs reuse them. `test/setup-tools.sh` fills that folder; inside the BBH network `DEVSECOPS_MAVEN_REPO` (a Maven repository with the content of Maven Central), `DEVSECOPS_JENKINS_REPO` (one with the content of `repo.jenkins-ci.org/releases`) and `DEVSECOPS_JDK_URL` (a JDK 21 `.tar.gz`) are tried before the built-in addresses, and `DEVSECOPS_JDK_HOME` names a JDK 21 of the agent. A value that is not an address is named in a `[TOOLS] [WARN]` line and the built-in address is used, a value equal to it in a `[TOOLS] [INFO]` line, and the setup fails only when the built-in address fails too. A complete folder is only read, so a read-only tool set in an agent image works. The script prints `ALL CHECKS PASSED` when the library is releasable, and it regenerates `examples/reports`, `documentation.html` and `documentation.md` on the way.

## What runs

### Static checks (`test/checks`)

| Check | What it proves |
|-------|----------------|
| `sandbox-lint.sh` | No construct that needs an administrator approval and no `map."${key}"` in `src`, `vars` and `ci/Jenkinsfile`, no static field |
| `undefined-calls.sh` | Every implicit call resolves to a declared method |
| `undefined-variables.groovy` | Every name in a library class is a local, a parameter or a field (catches `steps.error` in a class that has `script`) |
| `api-consistency.sh` | Every call on a library type matches a method with that argument count |
| `closure-calls.groovy` | No unqualified call inside a closure of a static method |
| `closure-field-writes.groovy` | No closure assigns a field of its own class |
| `noncps-calls.groovy` | No `@NonCPS` method calls a library method that is CPS-transformed (Jenkins would run it with the wrong result) |
| `jdk-whitelist.groovy` | Every JDK constructor, static method and static field used by the library is on the real script-security whitelist |
| `architecture.sh` | Adapters depend on the core and the ports, never the other way round |
| `vars-api.sh` | The shared methods resolve, every entry point declares its stages in order (the full pipeline equals security plus extended), a method that a custom Jenkinsfile may call keeps its former name as an alias of the new one (`sendPortalReport()` must call `sendOneViewReport()`), and every manifest updater is wired into the GoldenFix service |
| `no-comments.sh` | No comments and no commented-out code in `src`, `vars` and `ci/Jenkinsfile` |
| `ascii.sh` | `src`, `vars` and `ci` hold printable ASCII, tabs and newlines only |
| `docs-html.sh` | `documentation.html` is the rendering of `documentation.confluence` (regenerates it when it is not) |
| `docs-md.sh` | `documentation.md` is the Markdown rendering of `documentation.confluence` for Bitbucket (regenerates it when it is not) |
| `user-guides.sh` | `docs/USER_GUIDE_PORTAL.html` and `docs/USER_GUIDE_WITHOUT_PORTAL.html` are the rendering of their Markdown files (regenerates them when they are not; skipped without the Python module `markdown` and with another version than `tools/requirements-docs.txt` pins) |

The classes of the SQL and PL/SQL services (`DatabaseBuild`, `LiquibaseRunner`, `DatabaseDeployService`, `DatabaseSettings`, `LiquibaseOutput`) pass every check above; they added no check of their own.

### Compilation

`src` and `vars` are compiled with the compiler configuration of the sandbox (`GroovySandbox.createSecureCompilerConfiguration`), so a syntax error or an unsupported construct fails here. `ci/Jenkinsfile` is compiled too, so a syntax error in the CI build fails here and not on the first push.

### The OneView query script (`test/oneview/query-scenarios.sh`)

Takes the query script out of `OneViewConfigReader.groovy` and runs it with `sh` and the real `curl` against a small HTTP portal written in Python on `127.0.0.1`, which answers only `GET <path>/api/dso/config/<key>?format=json` with `Accept: application/json`. The scenarios check: one status, body and error file per key in key order, in a directory only the agent user can read; HTTP 200 with the sha256 hint of the body and the body byte for byte, UTF-8 included; the 403 and 404 problem details of the portal; a portal that answers 503 twice and is asked again until it answers; an unreachable portal reported as status `000` after three attempts, with the `curl` error and without the key; and that the script reads `ONEVIEW_URL`, `ONEVIEW_DIR` and `ONEVIEW_KEYS` only: it names no former variable, and a `DSO_PORTAL_URL`, `PORTAL_URL`, `DSO_PORTAL_DIR` or `DSO_PORTAL_KEYS` of the agent changes nothing, because the library resolves the former names before it starts the script. The retries make this step take about 20 seconds.

### The OneView upload script (`test/oneview/upload-scenarios.sh`)

Takes the two upload scripts out of `OneViewReportService.groovy` and runs the one for Linux and macOS with `sh` and the real `curl` against a small HTTP portal written in Python on `127.0.0.1`, which answers `POST <path>/api/dso/reports` as OneView does: with the stored report, which repeats the pipeline key of the request. The fake Jenkins of the sandbox scenarios records the script and never runs it, so only this check sees what the step prints. The scenarios check: the report arrives with its pipeline key; the console shows `[ONEVIEW] HTTP 201` and the answer with `"pipelineKey":"(not shown)"`, and no part of the output holds the key, also for an answer written with spaces around the colon; an answer of 500 ends the step with status 1 after the line with the status and the problem; an unreachable portal ends it with the status of `curl` (7), one `curl` error and no key; both scripts give `curl` the two time limits; and the script for Windows replaces the key of the answer before it prints it and names no former variable.

- `writeYaml` writes YAML into the in-memory workspace (and refuses to overwrite without `overwrite: true`), `readYaml(file:)` parses it and `fileExists` sees it; every `fileExists` and `readYaml(file:)` is recorded in `probes`, which is not part of the golden view, and every `fileExists` also in `probeFolders`, after the folder of its `dir` (`.` outside one);
- `copyArtifacts` copies the files that match the filter from the scenario's `upstream` map, records the filter and fails when nothing matches;
- `libraryResource` loads the real files under `resources/` and fails for a missing one; a scenario provides only the secret files that are not in the repository;
- `withEnv` and `withCredentials` set their variables only for their body (`string`, `usernamePassword` and `file` credentials), and `withCredentials` fails like Jenkins for a credentials ID listed in `missingCredentials`;
- `isUnix()` is switchable (`unix`), and `agentTmp` is the `WORKSPACE_TMP` of the agent (`null` leaves it unset);
- `parallel` runs the branches one after another in the order of the map; with `interleave` a branch whose `waitUntil` is false lets the next branch that has not started run (the first ones named in `parallelOrder`), after `waitSleepMs`, and `waitChecks` records who let whom run; the branch it lets run ends, with the branches that one lets run, before the waiting branch checks again, so a waiting branch sees one branch ended and another not ended only when the other has not started yet or is a branch that let it run, directly or through others; such a branch cannot end before the waiting one, so a `parallelOrder` in which a branch is let in by a branch it waits for, for example [Dependencies scan (Nexus IQ), SCA (SonarQube)], fails with `waitUntil never became true`;
- `readJSON` returns json-lib objects (JSONObject, JSONArray, JSONNull) like the real step; set `jsonLib = false` for plain Groovy maps;
- `dir` sets the current directory (`cwd`) for its body, and `dir` and `deleteDir` remove the files below a directory;
- `sha256(file:)` records the call and returns the SHA-256 of the in-memory file, and fails for a missing one; a scenario replaces it through `steps['sha256']`, for example with a step that throws like a plugin step Jenkins does not have;
- `zip` records the call and puts a placeholder file at `zipFile`; `withCredentials` binds every variable to `fake-<variable>`, which the D-SEC checks of the SQL and PL/SQL scenarios look for in every call, log line, file and InfluxDB line;
- `findFiles` matches `**/` as zero or one folder, not any number of folders, unless a scenario sets `deepGlob` on the fake, as the layout d runs do for the detection of `buildTool: sql`; the database steps themselves do not use `findFiles`;
- a `sh` script that calls `/api/dso/config/` is answered by the fake portal: for each key in `ONEVIEW_KEYS` it writes the status, body and error files below `ONEVIEW_DIR` as the portal would answer from the scenario's `oneView` map (key to key status, reason and configuration: 200, the 403 problem or the 404 problem), or from `oneViewAnswer` when a scenario wants another status, a `curl` error or a broken answer.

`test/sandbox/fixtures` holds in-memory port adapters for the GoldenFix end to end scenario. `InMemorySourceRepository` matches a pattern with a `/` against the whole path, skips the `excludeDirs` folders like `find` and records the pattern list of every search (`searches`); `RecordingPullRequestPublisher` records the pull request comments (`comments`) and fails them when `commentFailure` is set.

`test/fixtures` holds the configuration files of the library before the OneView integration: `defaults.yaml` (formerly `resources/defaults.yaml`), `CertScanner/config.yaml` (formerly `examples/CertScanner/config.yaml`) and `b815d55/com/bbh/config/ConfigLoader.groovy`, the loader that read them. `database/` holds the three repository layouts of chapter 14 (`layout-a`, `layout-b`, `layout-c`), the compile check and invalid-object scripts and the manifest the database code writes, and `database/oneview` the settings OneView writes for the three layouts, copied from its regression goldens (`backend/src/regressionTest/resources/regression/database-product-config.yaml`, `database-gradle-product-config.yaml` and `database-maven-product-config.yaml` at portal commit c483da8); no test reads the portal repository itself. `oneview/` holds documents a real OneView rendered for its demo services, and `oneview/rendered` the CertScanner `config.yaml` as the portal renders it, with the portal default `staticAnalysis.parallel: true` in `defaults` (rule R8). The pipeline and sandbox scenarios build their portal documents from `defaults.yaml` and `config.yaml`, so every pipeline run reads the same values as before. `test/fixtures/defaults.yaml` stays the frozen b815d55 file and is fed to every run without a key as `com/bbh/devsecops/defaults.yaml`; `resources/com/bbh/devsecops/defaults.yaml` is the production copy the DevSecOps team owns, and only the structure check of the compatibility scenarios reads it.

## Continuous integration (`ci/`)

`ci/Jenkinsfile` is the CI build of the library, the same file on both branches. A multibranch job of the BBH Jenkins (Bitbucket Server branch source, Script Path `ci/Jenkinsfile`) runs it on every push and every pull request, and every night on `DSOEnhancedWithoutPortal` and `main`. `Jenkinsfile.template` stays the starter Jenkinsfile of a project that uses the library.

| Stage | What it does | When it fails |
|-------|--------------|---------------|
| Workspace | `git clean -ffdx` | never |
| Tools | `ci/prepare.sh`: checks the commands of the suite, creates `build/ci/venv` with the newest Python 3.8 or later of the agent and the `markdown` version of `tools/requirements-docs.txt` (which needs Python 3.11 or later), and fills or checks the tool folder with `test/setup-tools.sh` | a missing command or tool stops the build |
| Library suite | `ci/suite.sh`: `test/run-all.sh` without `RECORD_GOLDEN`, `build/ci/junit/run-all.xml` from its log (`ci/junit.py`) and `ci/generated-files.sh` | FAILURE when a check fails or the run changed a committed file: a page rendered again, a recreated AppScan baseline or a golden file |
| Shared files | checks out the other branch of the library and the `main` branch of OneView and runs `tools/check-shared-files.sh` | UNSTABLE by default (`CI_SHARED_FILES=warn`), FAILURE with `fail`, not run with `skip` |

The build publishes the JUnit files, archives the logs, the diff of changed files, the example reports and the `.actual.txt` files, and publishes `examples/reports` as *Example reports*. Its parameters only apply to a run started with *Build with Parameters*: `CI_AGENT` (empty: the global variable `DEVSECOPS_CI_AGENT`, then `linux-agent`), `CI_TOOLS`, `CI_MAVEN_REPO`, `CI_JENKINS_REPO`, `CI_JDK_HOME`, `CI_JDK_URL` and `CI_PIP_INDEX_URL`, which become `DEVSECOPS_TOOLS`, `DEVSECOPS_MAVEN_REPO`, `DEVSECOPS_JENKINS_REPO`, `DEVSECOPS_JDK_HOME`, `DEVSECOPS_JDK_URL` and `PIP_INDEX_URL` only when they are not empty, `CI_SHARED_FILES`, `CI_SIBLING_BRANCH` (empty: the other branch) and `CI_ONEVIEW_REPOSITORY` (empty: `itss-coe-oneview.git` next to this repository). The values every build needs are global variables of the BBH Jenkins or of the agent, under the names the scripts read.

Not verified on the BBH systems: the plugins (Bitbucket Branch Source, Pipeline, JUnit, HTML Publisher, Timestamper), the agent label and its tools, the BBH Nexus paths of the mirrors and whether `scm.userRemoteConfigs` needs a script approval.

## Adding a scenario

1. Add the data and the expected values to the scenario list of the matching script.
2. Run `bash test/run-all.sh`.
3. When the AppScan baseline changes on purpose, delete `test/sandbox/baseline/appscan-commands.txt`, run the suite again and review the regenerated file before committing it.
