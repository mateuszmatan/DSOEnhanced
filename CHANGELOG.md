# Changelog

All notable changes to the DSOEnhanced Jenkins Shared Library are documented in this file.

## [Unreleased]

### Added
- **Continuous integration of the library** (2026-11-23, item 1.5 of `TODO.md`). `ci/Jenkinsfile` is the CI build of a multibranch job of the BBH Jenkins: on every push and pull request and every night on `DSOEnhancedWithoutPortal` and `main` it prepares the tools (`ci/prepare.sh`), runs `test/run-all.sh` with its results as JUnit (`ci/suite.sh`, `ci/junit.py`), fails when the run changed a committed file (`ci/generated-files.sh`) and compares the shared files (`ci/shared-files.sh`, `tools/check-shared-files.sh`), which marks the build UNSTABLE by default. `test/README.md` describes the job and its parameters.
  - *Tool set inside BBH.* `test/setup-tools.sh` fills the tool folder and is sourced by `test/run-all.sh`, which works as before without a new variable. `DEVSECOPS_MAVEN_REPO`, `DEVSECOPS_JENKINS_REPO` and `DEVSECOPS_JDK_URL` are tried before the built-in addresses, with a `[TOOLS] [WARN]` line for a value that is not an address and a `[TOOLS] [INFO]` line for one equal to the built-in address; `DEVSECOPS_JDK_HOME` names a JDK 21 of the agent. A download is kept only when it is complete, two builds on one agent take turns with a lock, and a complete folder is only read.
  - *Tests.* `test/ci/ci-scenarios.sh` runs the scripts against fakes; `ci/Jenkinsfile` is compiled and passes the ASCII, comment and sandbox checks. The user guides check runs only with the `markdown` version of `tools/requirements-docs.txt`, so another version no longer renders the pages again with other bytes.

- **Release of the safe artifact** (2026-11-23, item 1.4 of `TODO.md`). Stage 12, *Nexus delivery - Safe Artifact - 0 known Security Vulnerabilities*, publishes the files that stage 6 uploaded as `<tag>-SNAPSHOT` once more as the release `<tag>`, the build tag of `build.tag`, after the release gate, without building again. For Maven, Gradle, npm and pip nothing changes without a release repository: neither the bundled defaults nor the Global Settings of OneView set one, so stage 12 stays `NOT_REQUIRED` for them and the snapshot stays the delivered artifact, as before.
  - *The record of stage 6.* Every Maven, Gradle, npm or pip upload writes `nexus-delivery.json` with the coordinates, the snapshot version and the SHA-256 of each file. The security pipeline archives it and the extended pipeline copies it with `build.tag`; a security build of an older library has none, and the release stage is then `NOT_REQUIRED` with the reason.
  - *Stage 12.* Each file is taken from the workspace (full pipeline) or from `delivery.pull.outputDirectory` (extended pipeline) when its SHA-256 is the recorded one, else downloaded again from the snapshot repository and checked; then the release is looked up (Maven with `-U`, Gradle with `--refresh-dependencies`). A release with the same file passes without an upload, so the extended pipeline can run again for the same security build; one with another file fails the stage and is not replaced. Maven deploys with the goals of `delivery.push.maven` (or `delivery.maven`) and the flags of the library, Gradle with the wrapper of the service and `maven-publish`.
  - *Settings.* New block `delivery.release` in the Global Settings of OneView and in the library defaults, which a service may override; a value that the service and the Global Settings leave empty comes from the library defaults, as for `pluginRepositories`: `enabled` (default `true`), `repositoryUrl` (empty: no release), `repositoryId` (Maven login; default: the server id of the snapshot upload) and `credentialsId` (Gradle login, Username with password). A value that is not an address, an id or a boolean gets a `[WARN]` and the value of the Global Settings, else of the library defaults, which the line names; the snapshot repository is refused as the release repository with a `[WARN]`. Every service without a release names its reason in a `[NEXUS]` line: Nexus delivery off, `delivery.release.enabled: false`, no release repository, OpenShift (the image of stage 6), Flutter (its APK and IPA), no record of this build tag.
  - *npm and pip.* An npm or pip service uploads its package file with `delivery.push.maven` (Maven `deploy-file`) in stage 6 and is released like a Maven service; without that block it is not required in stage 6, with a line that says what to set.
  - *.NET.* `delivery.nuget.releaseSource`, with `delivery.nuget.releaseCredentialsId` (default: `credentialsId`), is the release feed of stage 12, pushed with `--skip-duplicate` (`-SkipDuplicate` for `nuget.exe`). Without it the package that stage 6 pushed to `delivery.nuget.source` is the delivered package and is no longer pushed a second time to the same feed. With Nexus delivery off, and on OpenShift, where stage 6 builds the image, stage 12 pushes the package to the release feed, else to `delivery.nuget.source`, as before. The extended pipeline, which builds no NuGet package, no longer looks for one.
  - *Node.js.* The release stage of the extended pipeline no longer runs the Node.js build: the released files are those of the security pipeline. `devSecOpsSteps.nexusReleaseDelivery` still takes its options map.
  - *SHA-256.* The `sha256` step of the Pipeline Utility Steps plugin; without it the run says so once and uses `sha256sum` (or `shasum -a 256`), or `Get-FileHash` on Windows. A file whose SHA-256 cannot be computed is not released.
  - *Tests.* New `test/sandbox/ReleaseScenarios.groovy` (`test/run-all.sh` runs it); the fake Jenkins has the `sha256` step; twelve golden files were recorded again, listed in `test/README.md`.

### Fixed
- **Nexus IQ counts in the metrics and the release gate** (2026-11-23, item 2.8 of `TODO.md`). The `security_findings` point of each service with `scanner=niq` carries the critical, high and medium counts of Nexus IQ for that service against the Nexus IQ limits of the library policy; before, every count was 0, because recording the stage result replaced the counts Nexus IQ had just written. The release gate lists them too: the *Release policy* card, `release-gate.json` and the `[RELEASE-GATE]` line name for example `gui Dependencies (Nexus IQ) critical 2 > 0`. The verdict does not change, as an orange Nexus IQ stage blocked the release before too. No setting changed.
  - *The `release_gate` point* counts every violation once. Before, the run read its own `release-gate.json` again after writing it, so the point counted each violation twice and repeated it with `(previous pipeline)`. A pipeline now reads that file once, before it writes its own.
  - *SAST counts.* A service whose SAST HTML report is missing records 0, as its log line says, instead of the counts of the service before it.
  - *History.* Points written before this release keep 0 for `scanner=niq` and the doubled `violations`, so panels built on `security_findings` and `release_gate` show a step on the day of the upgrade.
  - *Tests.* New checks in `StaticAnalysisScenarios.groovy` and `PipelineScenarios.groovy`; nine golden files were recorded again, listed in `test/README.md`.

### Changed
- **Static analysis at the same time on Windows agents** (2026-11-23, item 3.1 of `TODO.md`). Behaviour change for Windows agents: the full and security pipelines now run the unit tests, Nexus IQ, SAST and SonarQube at the same time there too, as on Linux, because `staticAnalysis.parallel` (default `true`; for a run with a key the checkbox *Run unit tests, Nexus IQ, SAST and SonarQube at the same time* of the Global Settings of OneView) and `DSO_STATIC_ANALYSIS_PARALLEL` now decide on every agent. Before, a Windows agent always ran them one after another and printed "Windows agent: Unit tests, Nexus IQ, SAST and SonarQube run one after another". No setting is new, and every `Jenkinsfile`, `devsecops_config.yaml`, `config.yaml` and setting of OneView works as before; the results, the gate and the metrics are those of the order one after another. To keep a Windows agent one after another, set `DSO_STATIC_ANALYSIS_PARALLEL=false` in the environment variables of its node properties (*Manage Jenkins → Nodes → `<agent>` → Configure → Node Properties*). On Linux and macOS agents nothing changes.
  - *SAST in a copy.* One PowerShell step copies the workspace with `robocopy` to `<WORKSPACE_TMP>\dso-sast` (`<WORKSPACE>@tmp\dso-sast` without `WORKSPACE_TMP`), outside the workspace, after it removed the copy of an earlier build and checked the path lengths and the junctions. SAST compiles and prepares there with `MSBUILDDISABLENODEREUSE=1` and `UseSharedCompilation=false`; a relative `appscanPath` is read below the workspace (`DSO_WORKSPACE`). The copy is removed after the scans are queued.
  - *Turns on the workspace.* Nexus IQ waits until the unit tests have ended, SonarQube until the unit tests and Nexus IQ have ended, because a .NET build in the workspace locks and rewrites the files Nexus IQ scans: "[STATIC] Windows agent: Dependencies scan (Nexus IQ) waits until Unit tests has ended - one build at a time in the workspace". New `devSecOpsApi.awaitWorkspaceTurn(stage)`, called by `devSecOpsSteps.dependenciesScan` and `sonarQube`; on Linux it runs no step. The waits are left out of the time one after another and of the time of each step in the *Manual Actions vs DevSecOps* table, and the note of the longest branch names the wait of that branch when it waited, for example "the longest of the 4 in parallel, with 3m 10s of waiting for Unit tests and Dependencies scan (Nexus IQ)".
  - *Fallbacks.* A copy that fails gives "[WARN] [STATIC] The workspace could not be copied for SAST (`<reason>`) - falling back: …" and the queued order, or the order one after another for a service with `asoc.<tool>` compile overrides, as on Linux. A copy that cannot be removed gives "[WARN] [STATIC] The SAST copy of the workspace (`<copy>`) could not be removed completely - the next build removes it before it copies the workspace". Neither fails the build.
  - *Windows IRX staging, in every order.* `robocopy` retries a locked file twice after 2 seconds, an exit code of 8 or more stops SAST instead of scanning fewer files, `sast_directory` and the AppScan client folders are left out for every service, `sast_directory` is removed after the prepare, and `removeStagedSources` names a folder that stays in a `[WARN] [SAST]` line.
  - *Not verified on a real Windows agent*: the scripts are checked as text and the order with the fake Jenkins only; the pilot is item 1.1 of `TODO.md`.
  - *Tests.* New `test/sandbox/WindowsStaticScenarios.groovy` (`test/run-all.sh` runs it); the fake Jenkins can let parallel branches take turns (`interleave`) and leave `WORKSPACE_TMP` unset. No golden file changed.
- **The library talks to ITSS COE OneView** (2026-11-22). The DevSecOps Management Portal is now ITSS COE OneView (OneView), the portal of the ITSS Center of Excellence that joins the areas DevSecOps, QA and Agile; its repository is `ITSS-COE-OneView` and its example address `https://oneview.apps.bbh.com`. Every existing `Jenkinsfile`, `config.yaml`, `devsecops_config.yaml` and Jenkins installation keeps working without a change:
  - *Jenkins variables.* `ONEVIEW_URL` and `ONEVIEW_AGENT` are the new names of `DSO_PORTAL_URL` and `DSO_PORTAL_AGENT`. The new name wins when it is set and can be used. A former name alone still works, and the console says so and how to rename it: `[ONEVIEW] DSO_PORTAL_URL is the former name of ONEVIEW_URL: it still works; rename it in Manage Jenkins > System > Global properties > Environment variables`. A new name that is blank or not an address is passed over for a former name that can be used, with a line that says why; the same value under both names is logged as removable; and the build stops, with a message that names `ONEVIEW_URL`, only when no name holds an address. A value that is refused is never repeated in a line or a message, and every line is logged once per build.
  - *The address on the reading agent.* The configuration read resolves its address before it takes an agent and again inside the node it reads on, as before this change: a value that the node properties of the reading agent set for `ONEVIEW_URL` or `DSO_PORTAL_URL` is the address of the request. New: that value is checked like the global one, so a build stops on the agent, before the request, when it is not an address.
  - *Jobs on an older release.* A job that is pinned to an older release of the library reads only `DSO_PORTAL_URL` and `DSO_PORTAL_AGENT`, and `PORTAL_URL` for its upload. The former variables stay set, with the same values as the new ones, until no job uses an older release; the line that says that they can be removed holds for this release only.
  - *Report upload: a run with a key uploads its report.* A run that read its configuration from OneView with the key or the keys of its Jenkinsfile (`pipelineKey`, `pipelineKeys`) now uploads its pipeline report without any further setting, with one `POST /api/dso/reports` for each key in their order, so that every pipeline of OneView the run names gets the report. Until now such a run uploaded nothing unless its job also set `DSO_PIPELINE_KEY`. The key of the upload is `DSO_PIPELINE_KEY`, then `PIPELINE_KEY`, of the build environment (one upload, as before), otherwise the keys of the Jenkinsfile, otherwise `oneview.pipelineKey`, then `portal.pipelineKey`, of the settings. A job variable that holds a key of its own Jenkinsfile gets one line that says that it can be removed. A failed upload of one key is one `[ONEVIEW]` line and the next key is still tried, and no upload changes the result of the build. The keys of the run are kept in `PipelineState` and written nowhere but into the payload: the lines show the hint of a key, the answer of OneView is printed with `"pipelineKey":"(not shown)"` in place of the key it repeats, and the report, the release gate, the run-state file and the metrics hold none. A job variable that holds a key of the Jenkinsfile in upper case is uploaded with the key as the run read it. The upload runs on the agent of the pipeline, which therefore needs HTTPS to OneView.
  - *Report upload: time limits.* The upload scripts of Linux, macOS and Windows pass `--connect-timeout 10 --max-time 60` to `curl`, so a OneView that does not answer holds a build for at most 60 seconds per key. An upload that needs longer now fails with its line, where it used to hold the build.
  - *Report upload: the address.* It is read from `ONEVIEW_URL`, then `DSO_PORTAL_URL`, then `PORTAL_URL`, then `oneview.url` of the settings, then `portal.url`: the settings block `oneview:` is the new name of `portal:`, which stays as the fallback. `ONEVIEW_URL` and `oneview.url` must be written as `https://<host>[:<port>][/<path>]`. The former names are taken as before this change, with every value that is not blank after its outer spaces and its trailing slashes are removed (an underscore in the host, a scheme in upper case, an IPv6 literal, `%xx`, no scheme, a query, a user and a password), so an installation that uploaded before uploads to the same address now. An address that is not written in that form is never printed: the line `[ONEVIEW] Uploading pipeline report to ...` then names the variable or the setting that holds it, and the line about the former name says that the value still works for the report upload and how to write it under the new name, where a plain rename would be refused. A former name that is blank is now passed over for the next name. A blank `oneview.url` or `oneview.pipelineKey` in front of a usable `portal.url` or `portal.pipelineKey` is logged as ignored because it is blank. The lines about the block name the place where it can be edited, the configuration file the run read or `resources/com/bbh/devsecops/defaults.yaml` of the library, and no longer the Global Settings, because OneView has no field for the block.
  - *Method names.* `devSecOpsApi.sendOneViewReport()` is the new name of `sendPortalReport()`, which stays as an alias; `test/checks/vars-api.sh` fails when the alias is removed.
  - *Names.* The log tag `[PORTAL]` is `[ONEVIEW]`; the messages, the report header and the examples say OneView; the build description of a failed read is `OneView unavailable`; and the Jenkinsfile examples show `'<key from OneView>'`. `PortalConfigReader`, `PortalReportService`, `PortalScenarios.groovy`, `PortalFixtures`, `test/portal`, `test/fixtures/portal` and `test/fixtures/database/portal` are `OneViewConfigReader`, `OneViewReportService`, `OneViewScenarios.groovy`, `OneViewFixtures`, `test/oneview`, `test/fixtures/oneview` and `test/fixtures/database/oneview`. The API paths `/api/dso/...`, `pipelineKey`, `pipelineKeys`, `DSO_PIPELINE_KEY`, `DSO_REQUIRE_PIPELINE_KEY`, the file names `devsecops_config.yaml` and `config.yaml`, and the InfluxDB and Grafana names are unchanged.
  - *Documentation.* Chapter 6 of `documentation.confluence` describes the variables, their former names, the order in which they are read, the report upload and every `[ONEVIEW]` line and stop message with the case that prints it; chapter 16 has the block `oneview:`; chapter 24 has the troubleshooting entries for the former names, the stop messages and the lines of the report upload.
  - *Verification.* `bash test/run-all.sh` ends with `ALL CHECKS PASSED`. `OneViewScenarios.groovy` has 217 checks (123 before the upload with the keys of the Jenkinsfile): each of the five rules of the former names for every name, the address read again on the agent, seven kinds of address that only a former name takes, the upload with one and with several keys, a failed upload of one key, the line for a job variable that equals a key, an address that is never printed, and every kind of line logged once per build. Seventeen changes of the library on scratch copies of the tree each made the checks named for them fail. The 29 pipeline runs of `PipelineScenarios.groovy` check that a run with keys uploads its report once for each key, that no key is in the log, the report, the release gate, the metrics or the run-state file, and that a run without a key uploads nothing. The new `test/oneview/upload-scenarios.sh` runs the upload script with the real `curl` against a local HTTP portal that answers as OneView does, and fails when the pipeline key that the answer repeats is in the output of the step. The 27 golden files were recorded again and compared with the files of before: the 16 of the pipeline scenarios gained the upload steps and lines of their two keys, and the 11 database goldens the time limits of `curl` and the line about `DSO_PIPELINE_KEY`; `test/README.md` describes the scenarios and the goldens. `roadmap.md` has section 29 and two new known limitations: the report upload was not run from a BBH Jenkins against the real OneView, and the library does not call `POST /api/dso/bitbucket/pull-requests/decorate` of OneView.

### Changed
- **Pull request comments with the fix AppScan recommends, read from the AppScan API.** After the SAST reports the library reads the open issues of the scan from `GET /api/v4/Issues/Scan/<scan id>` and, once per issue type, the fix recommendation from `GET /api/v4/Issues/<issue id>/Details`; no PDF or HTML report is parsed for the comments. A finding in a file the pull request changes is a comment of that file under its line (a comment of the file that names the line when Bitbucket does not take the line); a finding in a file the pull request does not change is written in one pull request comment per file, which names the file and the line. The files a pull request changes are read from Bitbucket Server (`changes`) or Bitbucket Cloud (`diffstat`). In the pull request of the developer every Nexus IQ upgrade is commented in the same way on the manifest that declares the dependency, with the version Nexus IQ recommends, and the dependencies left untouched are listed. Backward compatible: no new setting; when the API gives no list of issues a `[WARN]` line says so and the comments are built from the HTML report as before; when the changed files cannot be read every finding with a line is tried as a line comment. `examples/pull-request-comments.md` shows the comments.
- **The table of the report is now *Manual Actions vs DevSecOps*, with one line per step.** It replaces *Manual actions vs DevSecOps Automated Actions* and the box *Parallel stages*. The steps stand in the order of the pipeline, only those that ran: Build, Unit test with Code Coverage, Nexus IQ, SAST, SonarQube, Nexus delivery, Lower region test deployment, Regression, Smoke and Performance tests, DAST, Nexus delivery of the release and Higher region test deployment. *Step* shows the own time of the step; *Manual actions* adds 10 minutes of a manual trigger for the build, Nexus IQ, SAST, SonarQube and each test, 6 hours of the CyberTrack ticket for a DAST and nothing for the other steps (0 minutes for the SRM ticket of the higher region); *DevSecOps Automated Actions* shows of the steps that ran in parallel only the longest; the new column *Time gained* shows the saving in percent, and the line *Summary* gives the totals in seconds, minutes and percent; nothing is written under the table. When more than one service is configured, every step lists all configured services with the time the step took for each (the pipeline now records the time of every service in every stage). `report.manualEffort` has one key per step (`build`, `unitTests`, `nexusIq`, `sast`, `sonar`, `nexusDelivery`, `lowerDeployment`, `regression`, `smoke`, `performance`, `dast`, `higherDeployment`); the former keys `buildTrigger`, `scanTrigger`, `deployTrigger` and `testTrigger` are still read, with a `[WARN] [REPORT]` line that asks to rename them. The demo reports of `examples/reports` now record the stage *Build artifact* before the static analysis, as the pipelines run it, and are those of a run in parallel, the default.
- **The two branches of the library behave the same outside the portal** (items 2.1 to 2.3 of `TODO.md`); `SonarService`, `SonarScannerCommandBuilder`, `SecurityPullRequestService`, `SecurityPullRequestView`, `SecurityFindingsParser`, `SharedCatalogRepositoryService`, `BitbucketPullRequestPublisher` and `GitSourceRepository` are the same files in `DSOEnhancedWithoutPortal` and `main`:
  - *SonarQube.* A Gradle, Android or Maven service with analysis commands of its own (`tools.sonar.gradle.tasks`, `tools.sonar.maven.goals`) runs the plugin of its build; every other Gradle, Android and Maven service and every npm, pip and iOS service runs the `sonar-scanner` CLI. The CLI gets `tools.sonar.<tool>.flags` (for npm also `tools.sonar.node.flags`; of a Gradle, Android or Maven block only the `-Dsonar.` arguments), the sources of the service and the coverage report of pip and npm, and an argument of the service wins. The branch is passed as `-Dsonar.branch.name`; when the server refuses it, the analysis runs once more without it. `tools.sonar.branchAnalysis: false` skips the attempt with the branch; `true` is logged as the default that can be removed, and any other value falls back to `true` with a `[WARN]` line.
  - *Pull request decoration.* It runs for every service of the run, also on the open pull request of the analysed branch, adds at most `pullRequestDecoration.maxComments` line comments (default 25), leaves out findings below `pullRequestDecoration.sastMinSeverity` (default `MEDIUM`) and `pullRequestDecoration.sonarMinSeverity` (default `MAJOR`), and adds no comment that is already on the pull request. A wrong value falls back to its default with a `[WARN]` line and a value equal to the default is named in an `[INFO]` line.
  - *Shared version catalog repository.* The clone signs in with the SSH key, a bearer token or a username and password, as the push of the GoldenFix branch does, with the credentials of `scm.bitbucket` as the fallback.
- **One version of the user guides.** `docs/USER_GUIDE_PORTAL` and `docs/USER_GUIDE_WITHOUT_PORTAL` are merged with the copies of the portal and are the same files in both branches and in the portal. `tools/render-user-guides.sh` renders their pages, and the new check `test/checks/user-guides.sh` regenerates a page that does not match its Markdown file (skipped without the Python module `markdown`).
- OneView has the build tools npm, pip, Android and iOS, and its repository scan follows the detection order of the library.
- The auto-resolve of the settings detects the build tool in the same order as the library without the portal: `pubspec.yaml` (Flutter), `Podfile`, `Package.swift`, an Xcode project or workspace (iOS), `pom.xml` (Maven), the Gradle build files (Gradle, or Android with an `AndroidManifest.xml`), the .NET files, a Liquibase changelog, `requirements.txt`, `pyproject.toml`, `setup.py` or `Pipfile` (pip), `package.json` or `angular.json` (npm), and last only SQL and PL/SQL files (`sql`). A Python repository is now detected as `pip` instead of keeping the build tool of the Global Settings, a repository with a Liquibase changelog and a `package.json` but no other build file is detected as `liquibase`, and a value set for the service still wins.
- The Nexus delivery is one service, `NexusDeliveryService`. The snapshot of stage 6 is published under one tag per run, `<BUILD_NUMBER>-<yyyyMMdd-HHmmss>` in UTC, shared by every service of the run and written to `build.tag`, which the security pipeline archives and the extended pipeline copies with `pipeline-config.yaml` and `release-gate.json`.
- The snapshot is described under `delivery.push`: `delivery.push.maven` (goals and the artifacts by file name, extension and classifier) and `delivery.push.gradle` (repository, group, artifact and the artifacts to publish). A Gradle service publishes the matched files with its own wrapper on a generated project in the temporary folder of the build (`resources/com/bbh/devsecops/nexus-delivery.gradle`), which is removed afterwards. The earlier `delivery.maven` with `build.buildPath` still works. A Gradle service without `delivery.push.gradle.artifacts` is not required in stage 6 and its UrbanCode versions keep the build number.
- `delivery.nexusDeliveryEnabled` of a service wins over `deploy.<target>.rd.nexusDeliveryEnabled`, and every console line names the setting that was read.
- The extended pipeline deploys a VM service to the lower test region with UrbanCode Deploy (DOD), as the full pipeline does; the component versions carry the tag of `build.tag`, otherwise the build number.
- The deployment repository of an OpenShift service (`deploy.openshift.rd.deploymentPath`) is checked out in the Monitor stage, without switching the current service; the SAST scanning and Nexus IQ GoldenFix pipelines leave it out.
- The release delivery (stage 12) then pushed the NuGet package of a .NET service with `delivery.nuget.source`. For every other build tool the release delivery of the safe artifact was not implemented then (*Release of the safe artifact* under *Added* adds it): the service was not required with a `[NEXUS]` line and the snapshot of stage 6 stayed the delivered artifact. The stage no longer runs `./gradlew publish` or `mvn deploy`, and the extended pipeline then ran the Node.js build only before a release delivery that was available (both changed by *Release of the safe artifact* under *Added*).
- The `artifact_version` of the `build_evidence` point is the pinned `rd.buildTag`, otherwise the tag that the service delivered (the version of the zip for a Liquibase service with a database block), otherwise the build number.
- SAST runs through the HCL AppScan on Cloud REST API v4: SAClientUtil only generates the IRX, which is uploaded (`FileUpload`) and queued (`Scans/Sast`) with `curl` (`curl.exe` from a batch step on Windows agents); the status is polled and the HTML and PDF reports are generated and downloaded through the API. The reports and the severity counts leave out the issues with the `Noise` status.
- SAST and DAST of every service sign in with the one API key of the functional AppScan on Cloud user, `asoc.keyId` and the Jenkins Secret text credential named in `asoc.token` of the library defaults (`resources/com/bbh/devsecops/defaults.yaml`). A service sets only its `appId`; a `keyId`, `token` or `credentialsId` under `asoc`, `sast` or `dast` of a service is ignored with a `[WARN]` line that names it, and a service without a key ID no longer stops the build at the start.
- The run signs in once and reuses the bearer token for SAST and DAST, signing in again after 90 minutes. The sign-in body is written to the temporary folder of the build and removed after the call, and the `curl` calls run without shell tracing, so neither the key secret, the bearer token nor the proxy password reaches the console. The proxy password is read from `proxy.pass` when `PROXY_PASS` is not set.
- GoldenFix changes only the last number of a version (the patch): `1.2.3` may become `1.2.4`, never `1.3.0`. The fallback to a minor or major upgrade when Nexus IQ offers no patch version is removed; such a dependency is left untouched. Pre-releases are never proposed, and every manifest applies the rule to the version it declares.
- GoldenFix proposes only direct dependencies: `goldenFix.onlyDirectDependencies` is removed. `overrides`, `resolutions` and `constraints*.txt` are changed only for components that Nexus IQ marks as direct.
- The GoldenFix pre-check build is mandatory: `goldenFix.verify.enabled` is removed, and a change that no build can verify ends `NOT_VERIFIED` without a pull request.
- The GoldenFix pre-check runs the unit tests of the project with the proposed versions: `mvn -B -q test`, the Gradle `test` task, `npm test` (with `CI=true`, when `package.json` has a `test` script other than the `npm init` placeholder), `pytest` in a temporary virtual environment after a real `pip install`, `flutter test` or `dart test` when a `test` folder exists, and `dotnet test`. A failing test lowers the versions like a failing build. Windows agents get PowerShell forms of every check; a .NET project built with the classic `MSBuild.exe` is still built without its tests. `goldenFix.verify.commands` still replaces the check of an ecosystem.
- The shared version catalog repository is verified before its pull request: its own build, or the application built with the changed catalog files; otherwise no pull request is raised there.
- A dependency left untouched because Nexus IQ offers only a minor or major upgrade is listed in the report and in the metrics under the upgrades that were not applied automatically, with the version Nexus IQ offers.
- The full and security pipelines run the unit tests, Nexus IQ, SAST and SonarQube at the same time, as parallel branches of the stage *Static analysis*, and the full and extended pipelines run the regression, smoke and performance tests and DAST at the same time in the new stage *Dynamic analysis*. Windows agents kept the static stages one after another until *Static analysis at the same time on Windows agents* (under *Changed* above).
- SAST compiles and queues its scans in a copy of the workspace (`<WORKSPACE_TMP>/dso-sast-workspace` on Linux and macOS), which is removed after the queue, so its compile never changes the files the other branches read; SonarQube of a service waits until the unit tests of the services of its source folder have written their coverage. When the copy cannot be made, the run logs a `[WARN]` line and falls back to SAST queuing first while the other three run one after another.
- A value of `staticAnalysis.parallel`, `dynamicAnalysis.parallel` or their environment variables that is neither `true` nor `false` no longer counts as `false`: the console names it in a `[WARN]` line and the default `true` is used. A value equal to the default is named in an `[INFO]` line, so that it can be removed.
- A value of a service whose kind differs from its default, such as text for a number, a word other than `true`/`false`/`yes`/`no`/`on`/`off`/`1`/`0` for a switch, or a map for a list, falls back to the default with an `[INIT] [WARN]` line that names the key, the value and the default: the library default without a key, the value of the Global Settings with a key. A number in quotes is kept.
- Without a key, a name of `projectNames`, `PROJECT_NAMES` or `PROJECT_NAME` that the file does not have is left out with an `[INIT] [WARN]` line instead of stopping the build; when no name is left, the run builds every service of the file, as without the parameter. With a key, a name that is not a service of the pipeline keys still stops the run.
- Without a key, every key of a service whose value is the one the library uses without it, the library default or the value the auto-resolve finds in the repository (`buildTool`, `tools.sonar.projectKey`, the Liquibase and Node.js values and the others it fills), is named in an `[INIT] [INFO] ... - the key can be removed from devsecops_config.yaml` line, and so is a `projectNames` that lists every service of the file in its order.
- A Gradle or Maven step (build, unit tests, SonarQube, SAST compile) that fails because a plugin is not in the repositories of the build runs once more with the plugin repository of the BBH Nexus (`pluginRepositories.gradle` and `pluginRepositories.maven` of the Global Settings, otherwise of the bundled defaults): Gradle with an init script that puts it first in the plugin and buildscript repositories, Maven with a copy of the user settings that adds it in an active profile. The console names the plugins and where to add the repository, and the later steps of the same folder use it at once. `pluginRepositories.enabled: false` switches the retry off. An empty repository takes the one of the bundled defaults, and an address that is not a plain http or https address is named in a `[WARN] [BUILD]` line and replaced by it.

### Fixed
- **Auto-resolve of the settings next to a database block**: the auto-resolve resolves each service into its own copy of the settings. Before, the SonarQube project key, the Liquibase commands, the Cypress switch and the Flutter platform it filled for one service were written into the nested maps that every service shares with the Global Settings after the merge, so a later service without `tools.sonar.projectKey` read the issues of the first service's project, and a Gradle service without its own `tests` next to a Liquibase service ran the `validate` command filled for the Liquibase service. A Liquibase service with a database block (`database.changelogFile`) keeps its settings and gets only `tools.sonar.projectKey`: the auto-resolve adds no `build.liquibase` or `tests.unitTests.liquibase` commands, no Node.js stage 0 or Cypress switch and no `deployTarget` or `appName` to it, and it never sets `buildTool: liquibase` for a service with `database.changelogFile`, so the detection cannot switch on the deployments of a block. A service without a block gets every key of the auto-resolve as before.
- **SonarQube defaults next to a database block**: the library writes no `sonar-project.properties` for a service with a database block and adds no `sonar.branch.name` to one, and the scanner of the block gets `-Dproject.settings` with an empty file in the work folder of its step (unless `tools.sonar.liquibase.flags` names a file of its own), so it reads no `sonar-project.properties`. Before, the defaults written before the scan of the block (`sonar.language=sql`, `sonar.modules` and per-module sources and tests from `pom.xml` or `settings.gradle`) were read by a block scanner running at the workspace root: in a Gradle multi-module repository such as layout b the scan became a multi-module analysis of the Java module under the project key of the database service, or failed; and a file written for another service of the same run in the same folder reached the block the same way. A service without a block writes and reads the defaults as before; one listed after a database block in the same workspace now writes its own defaults instead of finding those written for the block.
- **SAST folders of each service**: AppScan prepares the IRX of each service from that service's own `sourceDir`, `includedDirs` and `excludedDirs` (Windows agents use `sourceDir` and `includedDirs` and do not apply `excludedDirs`). Before, every IRX of a multi-service run was prepared from the `sourceDir`, `includedDirs` and `excludedDirs` of the last service listed (on Windows: its `sourceDir`), so the folders of the other services were scanned only where they lay inside that scope, and the last service's scope was scanned, and counted in the SAST counts and the gate, once per service. Products whose services differ in `sourceDir`, `includedDirs` or `excludedDirs` can see different SAST counts and gate results after the upgrade.
- **SonarQube folder of a Liquibase service with `tools.sonar.liquibase.dir`**: the scanner runs inside that folder, and every path the library adds is given from it: `-Dsonar.sources=.` without a database block; with a block the package folder, the utPLSQL test folder and its exclusion, and the utPLSQL coverage and test execution reports as copies whose file paths start below that folder. The settings check refuses a block whose package folder or utPLSQL test folder lies outside `tools.sonar.liquibase.dir`. Before, the scanner got `-Dsonar.sources=<dir>` inside `<dir>`, a folder that does not exist, so the analysis failed unless `tools.sonar.liquibase.flags` moved `-Dsonar.projectBaseDir`. Remove such a workaround after the upgrade, or set `tools.sonar.liquibase.sources`.
