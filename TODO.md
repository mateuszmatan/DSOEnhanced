# DevSecOps: to-do list

Open work for the DSOEnhanced library (branches `DSOEnhancedWithoutPortal` and `main`) and ITSS COE OneView, after the review of the three sources on 2026-11-20. The same file is kept in all three sources. What was delivered is in `roadmap.md` and the changelogs; the overview for senior management is `docs/MANAGEMENT_OVERVIEW.md`.

Rules for every item: change `DSOEnhancedWithoutPortal` first, then `main` and the portal, so that the three stay consistent; keep `config.yaml`, `devsecops_config.yaml` and the `Jenkinsfile` backward compatible; a setting that is given wins, a wrong one falls back to the default with a log line, and the build fails only when the default fails as well.

## Priority 2: consistency of the three sources

| 2.12 | **InfluxDB points of a run with several services.** `PipelineMetrics` writes the `vulnerabilities` points with `scanner=sast` and `scanner=dast` with the counts of the last service scanned in the run, while those with `scanner=nexusiq` and `scanner=sonar` add up the critical, high and medium counts of all services, count a Nexus IQ application or SonarQube project key that several services share once for each of them, and write `low` as 0. ## Done on 2026-11-26

- 2.9: the default values that the DevSecOps team keeps for every service have one name, *Library defaults*, the name of their page in OneView (Admin, Library defaults), instead of Global Settings, global settings or global defaults. Both library branches use it in their console lines. Where a line names the copy it means, it is the Library defaults of OneView, which a run with a pipeline key reads, for example "[POLICY] Library defaults from OneView, projects cannot change them:", or the library defaults of the library release (`resources/com/bbh/devsecops/defaults.yaml`), which a run without a key and every run of `DSOEnhancedWithoutPortal` read. The lines of `main` about the Liquibase CLI, the Oracle driver and the allowed databases of a database service keep their meaning and name OneView in every run, also without a key, for example "set tools.oracleJdbc.path, or tools.oracleJdbc.url with its sha256, in OneView under Admin, Library defaults"; a run without a key takes the tools from the library release or from the service in `devsecops_config.yaml`, and the allowed databases from the library release (item 2.13). OneView uses it in its messages, help texts and import notes, for example "the pipelines deploy only to the databases the DevSecOps team allows in the Library defaults", and so do the documents of the three sources. The page and the menu of OneView stay as they are, and no setting, key, class, REST path or column changed.
- 2.10: the library reports its pull request decorations to OneView, and OneView records them and shows them on the page of the pipeline. In both library branches `SecurityPullRequestService` hands a `DecorationRecorder` one record of each pull request it commented on or opened: the pull request of the analysed branch (`BRANCH`), the static security pull request (`STATIC`) and the DAST pull request (`DAST`), with the comments it added and the first 200 findings. `main` sends each record right after the decoration with `POST /api/dso/bitbucket/pull-requests/decorate`, with the pipeline key of the run (the key of the job, else the key of the service) and the job, build, branch and commit of the run, to the address and in the way of the report upload; a failed report is a console line and changes neither the build nor the comments, and `DSOEnhancedWithoutPortal` records nothing. OneView keeps the path, the request and the answer of that endpoint, which no longer posts to Bitbucket: it finds the pipeline by the active key, otherwise by the job, keeps the first 500 findings and never stores the pipeline key (changeset `052-pull-request-decorations`), and the section *Pull request decorations* of the pipeline page lists the newest 20 with their findings (`GET /api/pipelines/{id}/pull-request-decorations`). A request of an older client stays valid. The roadmap of both branches no longer says what does not hold.
- 3.5: the front end of OneView passes the Prettier check, `npx prettier --check .` in `frontend` with the settings of `.prettierrc` and Prettier 3.9.9, the version of `frontend/package-lock.json`. ## Done on 2026-11-25

- 3.1: on Windows agents the full and security pipelines run the unit tests, Nexus IQ, SAST and SonarQube at the same time too, as on Linux. SAST compiles and prepares its scans in a `robocopy` copy of the workspace outside it (`<WORKSPACE_TMP>\dso-sast`), and the unit tests, Nexus IQ and SonarQube take turns on the workspace, because a .NET build there locks and rewrites the files Nexus IQ scans; the waits are left out of the times of the report. No setting is new: `staticAnalysis.parallel` and the Library defaults checkbox decide as on Linux, and `DSO_STATIC_ANALYSIS_PARALLEL=false` in the node properties of an agent keeps that agent one after another. Both library branches and the help texts of OneView; the pilot of 1.1 runs it on a real Windows agent.
- 2.5: the portal has the build tool MSBuild, *C# / .NET Framework (MSBuild)*, as a choice of its own next to C# / .NET, in the form, the Library defaults, the import, the rendering and the database (changeset `050-msbuild-build-tool`). It renders `buildTool: msbuild` with the same `.dotnet` blocks of `build`, `tests.unitTests`, `tools.sonar` and `asoc` and the same NuGet feeds as C# / .NET, which the library reads for `msbuild` as well, so the library builds the service with NuGet.exe and MSBuild.exe instead of choosing the mode from the projects and the agent. An import of `msbuild`, `vs`, `visualstudio` or `netfx` becomes MSBuild instead of C# / .NET and reads the `.msbuild` blocks where the library takes them; every saved service keeps its build tool.
- 2.7: the portal has the Liquibase steps that the library runs after the build and after the unit tests of a Gradle, Android, Maven or .NET service (`build.liquibase`, `tests.unitTests.liquibase`) and after the SAST compile of a Gradle or Maven service (`asoc.liquibase`), and the SonarScanner version (`tools.sonar.sonarScannerVersion`) for every build tool but C# / .NET and MSBuild, in the form, the import, the rendering and the database (changeset `051-liquibase-step`). The import turns `tools.sonar.liquibase` of a Gradle, Android or Maven service into flags of its SonarQube tasks or goals, the only analysis that reads it. `delivery.liquibase` has no field: no stage of the library reads it, so the import notes it as not imported. Every saved Flutter service keeps its version, and a client that reads it from `flutter.sonarScannerVersion` and sends it there keeps working; the old column stays until a later release (3.9).
- 2.11: on a Linux or macOS agent the SAST compile of an Android service runs Gradle, as its build (`asoc.gradle`, else `build.gradle`), and then the Liquibase SAST step (`asoc.liquibase`, else `build.liquibase`), and an npm, pip, iOS or Flutter service has no compile step: the console says so, and the IRX is prepared from the sources. Before, the SAST stage of these five build tools stopped with "Build Tool is not specified in configuration" while `asoc.doCompile` was on, the default. No setting changed, and Gradle, Maven, Liquibase, SQL, C# / .NET and MSBuild services and Windows agents run as before. Both library branches; OneView no longer advises to untick "Compile before preparing the IRX", says what the compile runs for each build tool and offers an Android service the Liquibase step after the compile in the form, the API and the import, without a change of the database or of the rendering of a saved service.
