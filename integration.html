DevSecOps Library — Integration Guide

How to put a new BBH application onto the shared DevSecOps pipeline, step by step. Written so that you can follow it without being a Jenkins specialist.

How to use this guide

Work through Part 1 and Part 2 once for your application — they are the same whichever pipeline you end up running. Then go to the one chapter in Part 3 that matches the pipeline you want, and follow it to the end.

Every step says who does it. Where a step has to be done by another team, it says which one and what to ask for.

You do not need to write any pipeline code. Your application needs exactly two new files: a Jenkinsfile of about five lines, and a config.yaml that describes your application. Everything else comes from the shared library.

1 Part 1 — Before you start

1.1 The BBH systems your pipeline will use

All of these run inside the BBH network. You will need an account or an entry in each of the ones your pipeline uses.

SystemAddressWhat it does for you
Bitbucketrdtools.testbbh.com:7990Stores your source code, your Jenkinsfile and your config.yaml, and receives the automatic dependency-upgrade pull requests
JenkinsYour BBH Jenkins instanceRuns the pipeline. Jobs run on OpenShift agents or on VM agents
SonarQube Communitytools.bbh.com/sonarCode quality analysis and the quality gate
Nexus IQtools.bbh.com/IQScans your third-party dependencies for known vulnerabilities
Nexus repositorytools.bbh.com/nexusStores the artifacts and container images your pipeline publishes
HCL AppScan on Cloudbbh.cloud.appscan.comSecurity scanning of your source code (SAST) and of your running application (DAST)
InfluxDB / GrafanaBBH monitoring instanceOptional. Collects the pipeline metrics and the DORA figures
How AppScan is reached. AppScan is outside the BBH network, so the pipeline goes through the BBH proxy tstproxy.bbh.com:9090 using the dedicated service account PROXY_ASOCJenk. The pipeline obtains that account's password at run time from OIS (oisapi.bbh.com) using a certificate and the internal helper scripts. You do not configure any of this. The certificates and scripts are maintained by the DevSecOps platform team and are deliberately not stored in the library repository. If your agent cannot reach AppScan, this is the part to raise with them.

1.2 What you need to have ready

  1. A Bitbucket repository for your application
    Who: you or your team lead
    Your code must already be in Bitbucket on rdtools.testbbh.com:7990. Note the project key and the repository name — you will need them later, for example MYAPP and myapp.
  2. A build that runs on its own
    Who: a developer on your team
    The application must build with Gradle, Maven or Flutter without anyone typing anything. Check this by running the build on a clean machine first. If it asks a question or needs a manual step, the pipeline cannot run it.
  3. A unit test task that produces a coverage report
    Who: a developer on your team
    The pipeline requires line coverage of at least 60% and this cannot be lowered per project. The report must be JaCoCo XML for Gradle and Maven, or an LCOV file for Flutter. Without a coverage report the stage turns orange, because the requirement cannot be verified.
  4. A Jenkins agent label
    Who: ask the Jenkins administrators
    Ask which agent label your job should use, for example linux-agent. The agent needs Java, your build tool, and curl, git and python3. Agents used for automatic dependency upgrades must be Linux or macOS.
  5. Confirm the shared library is registered
    Who: ask the Jenkins administrators
    Ask them to confirm that the global library DevSecOpsJenkinsLibrary is configured in Manage Jenkins → System → Global Pipeline Libraries. This is done once per Jenkins instance, not once per application.

2 Part 2 — Register your application in the BBH tools

Do this before the first pipeline run. Each tool gives you an identifier that you will paste into your config.yaml. Keep a note of the four values as you go.

2.1 Nexus IQ — dependency scanning

Where: tools.bbh.com/IQ  ·  Who: you, or the Nexus IQ administrators if you cannot create applications
  1. Sign in and open Organizations & Policies Find the organisation your team belongs to. If you do not know which one, ask your team lead.
  2. Create a new application Use a clear name such as MyApp-GUI. Nexus IQ will also ask for an Application ID, which is the short public identifier — this is the value you will need.
  3. Confirm a policy is assigned The application must inherit your organisation's policy, otherwise the scan reports nothing. The administrators can confirm this.
  4. Write down the Application ID You will put it in config.yaml as tools.nexusIq.application.
The pipeline fails the dependency stage if the application does not exist in Nexus IQ, so do this step before the first run.

2.2 SonarQube — code quality

Where: tools.bbh.com/sonar  ·  Who: you
  1. Create the project Sign in, choose Create Project → Manually, and give it a display name such as MyApp-GUI and a project key such as myapp-gui. The key must be unique across BBH — prefixing it with your application name is the safest choice.
  2. Generate a token to read results back Open your user menu → My Account → Security and generate a token. Give it to the Jenkins administrators to store as a Secret text credential, and note the credential ID they give you.
  3. Optional: generate a badge token In Project Settings → Badges you can copy a badge token. Adding it to the configuration makes the quality metrics appear directly in the pipeline report.
  4. Write down the project key and the credential ID They go into config.yaml as tools.sonar.projectKey and tools.sonar.authToken.
Flutter applications. SonarQube Community has no Dart analyser, and the library does not need one. It converts your coverage and your dart analyze findings into the formats SonarQube accepts from any language. You do not have to install anything — just create the project as above.

2.3 HCL AppScan — SAST (scanning your source code)

Where: bbh.cloud.appscan.com  ·  Who: the DevSecOps team creates the application; you note the ID
  1. Request an AppScan application Ask the DevSecOps team to create an application for your product in AppScan on Cloud. Give them the application name and your team.
  2. Receive the Application ID They will send you an identifier that looks like 109f44ac-cc06-4ca0-884e-d944904f7019. This goes into config.yaml as appId.
  3. Receive the API key ID The key ID looks like bbh_b81fbc9f-... and goes into config.yaml as asoc.keyId. The matching secret is not put in your file — it lives in the Jenkins credential hcl-app-scan-acount.
  4. Confirm your agent can reach AppScan Ask the DevSecOps team to confirm the proxy service account and the OIS certificate are installed on the agent label you were given in step 1.2.4. This is the single most common reason a first SAST run fails.
Never put the AppScan key secret, the proxy password or any certificate into config.yaml or into Bitbucket. Secrets belong in the Jenkins credentials store. The library reads them from there at run time.

2.4 HCL AppScan — DAST (scanning your running application)

Where: bbh.cloud.appscan.com  ·  Who: you and the DevSecOps team

DAST scans a running instance of your application, so it only applies if you have one deployed in a test environment. If you do not, set dast.enabled: false and the pipeline reports the stage as not required instead of failing.

  1. Have a deployed test instance Note its URL, for example http://rdltaapps1.testbbh.com. This goes into config.yaml as dast.targetUrl.
  2. Request an AppScan Presence Because your application is inside the BBH network and AppScan is outside it, AppScan needs a Presence — a small agent inside the network that performs the scan. Ask the DevSecOps team to provide one and give you its ID.
  3. Decide whether the scan needs to log in If the parts of the application worth scanning are behind a login, provide a dedicated test account. Give the credentials to the DevSecOps team rather than putting them in the file.
  4. Write down the target URL and the Presence ID They go into config.yaml as dast.targetUrl and dast.presenceId.

2.5 Nexus repository — where artifacts are published

Where: tools.bbh.com/nexus  ·  Who: ask the Nexus administrators

Only needed if your pipeline publishes artifacts or container images. Ask for a snapshot repository and a release repository for your application, and for an account that may deploy to them. If you deploy to OpenShift, ask for the Docker registry path as well.

2.6 Checklist before you continue

You should now have, written down: the Nexus IQ application ID, the SonarQube project key and token credential ID, the AppScan application ID and key ID, and — if you use DAST — the target URL and Presence ID. If any of these is still missing, finish Part 2 before going on.

3 Chapter 1 — Full pipeline devSecOpsPipeline

When to choose this one

One Jenkins job that does everything: build, unit tests, all three security scans, code quality, publishing, deployment to two environments, functional and performance tests, and the dynamic security scan. Choose it when a single job covering the whole flow is acceptable and the run time is not a problem.

Thirteen stages: source checkout · unit tests with the coverage gate · Nexus IQ dependency scan · AppScan SAST · SonarQube · Nexus snapshot delivery · deployment to the lower environment · regression tests · smoke tests · performance tests · AppScan DAST · Nexus release delivery · deployment to the higher environment.

Steps

  1. Add the Jenkinsfile to the root of your repository
    Who: a developer on your team
    Create a file called exactly Jenkinsfile, with no extension, containing: 
    @Library('DevSecOpsJenkinsLibrary') _

devSecOpsPipeline(
    projectNames: 'my-app',
    agentNames:   ['linux-agent']
)
    projectNames must match the keys you use in config.yaml in the next step. agentNames is the agent label you were given in Part 1.
  2. Add config.yaml to the root of your repository
    Who: a developer on your team, using the values from Part 2
    projects:
  my-app:
    appId:        "<AppScan application ID>"
    buildTool:    gradle
    deployTarget: vm
    javaPath:     /usr/lib/jvm/java-17-openjdk

    asoc:
      url:   "https://bbh.cloud.appscan.com"
      keyId: "<AppScan key ID>"

    tools:
      sonar:
        projectName: "MyApp"
        projectKey:  "myapp"
        serverUrl:   "https://tools.bbh.com/sonar"
        authToken:   "<Jenkins credential ID of your Sonar token>"
      nexusIq:
        application:   "<Nexus IQ application ID>"
        serverUrl:     "https://tools.bbh.com/IQ"
        credentialsId: "nexusiqP"
        scanPatterns:  ["**/build/libs/*.jar"]

    build:
      gradle:
        tasks: ['clean', 'build']

    tests:
      unitTests:
        gradle:
          tasks: ['test', 'jacocoTestReport']
        unitTestResult: 'build/test-results/test/*.xml'
      smoke:
        jobs:
          - name: "MyApp - smoke"
            type: local
            job:  "myapp/smoke-tests"
      regression:
        jobs:
          - name: "MyApp - regression"
            type: local
            job:  "myapp/regression-tests"
      performance:
        jobs:
          - name: "MyApp - performance"
            type: local
            job:  "myapp/performance-tests"

    dast:
      enabled:    true
      targetUrl:  "http://rdltaapps1.testbbh.com"
      presenceId: "<AppScan Presence ID>"

    scm:
      bitbucket:
        url:           "http://rdtools.testbbh.com:7990/projects/MYAPP/repos/myapp"
        credentialsId: "<your Bitbucket credential ID>"

    deploy:
      vm:
        rd:
          host:         "rdltaapps1.testbbh.com"
          user:         "taadmin"
          deployDir:    "/opt/ta/MyApp/deployment"
          deployScript: "scripts/deployment/deploy.sh"
        qc:
          host:         "qcltaapps1.testbbh.com"
          user:         "taadmin"
          deployDir:    "/opt/ta/MyApp/deployment"
          deployScript: "scripts/deployment/deploy.sh"
    Use buildTool: maven or flutter if that is what your project uses, and replace the build and tests blocks accordingly. The full list of options with their defaults is in config.yaml.template in the library repository.
  3. Create the test jobs in Jenkins
    Who: you, together with your QA colleagues
    Smoke, regression and performance jobs must exist before the pipeline reaches those stages. They can run on this Jenkins or on another one. If a suite is not ready, leave the job name empty — the stage reports it as not configured and turns orange rather than failing the run.
  4. Commit and push both files to Bitbucket
    Who: a developer on your team
    Push them to the branch you want the pipeline to build, usually develop or main.
  5. Create the Jenkins job
    Who: you, or the Jenkins administrators
    In Jenkins choose New Item, give it a name such as MyApp-devsecops-pipeline, and choose Pipeline. In the job configuration set Definition to Pipeline script from SCM, SCM to Git, the repository URL to your Bitbucket repository, the credentials to your Bitbucket credential, and the Script Path to Jenkinsfile. Save.
  6. Run it once and let it define its parameters
    Who: you
    Press Build Now. The first run registers the build parameters and may stop early — this is normal. Run it a second time; from then on you will see Build with Parameters with AGENT_NAME and DEPLOY_HIGHER_ENV.
  7. Go to Part 4 and check the result Read the report and fix whatever it names.
About the higher environment. DEPLOY_HIGHER_ENV is off by default. The pipeline only deploys there when you tick it and everything else is green, so a promotion is always deliberate.

4 Chapter 2 — Security pipeline devSecOpsSecurityPipeline

When to choose this one

The first half of the flow, meant to run on every commit: it is fast, it needs no deployed environment, and it gives developers security feedback quickly. It pairs with Chapter 3, which runs the slower half on demand.

Six stages: source checkout · unit tests with the coverage gate · Nexus IQ dependency scan · AppScan SAST · SonarQube · Nexus snapshot delivery.

It also archives your config.yaml and the release decision so that the extended pipeline can pick them up, and it can start the extended job automatically.

Steps

  1. Add the Jenkinsfile
    Who: a developer on your team
    @Library('DevSecOpsJenkinsLibrary') _

devSecOpsSecurityPipeline(
    projectNames: 'my-app',
    agentNames:   ['linux-agent']
)
  2. Add config.yaml, without the deployment and test sections
    Who: a developer on your team
    Start from the file in Chapter 1 and remove the dast, deploy and tests.smoke / regression / performance blocks — this pipeline does not use them. Keep appId, asoc, tools.sonar, tools.nexusIq, build, tests.unitTests and scm.bitbucket.
  3. Name the extended job, if you will use one
    Who: you
    If you plan to follow Chapter 3, add this so the security pipeline knows which job to start: 
        jenkins:
      pipeline:
        extendedPipeline: "MyApp/MyApp-extended-pipeline"
    Use the full Jenkins path of the job you will create in Chapter 3. You can add this later.
  4. Commit, push, and create the Jenkins job
    Who: you
    Create it exactly as in Chapter 1 step 5, naming it something like MyApp-security-pipeline.
  5. Turn on automatic builds
    Who: you
    Because this pipeline is meant to run on every commit, enable a build trigger in the job configuration — either a Bitbucket webhook or Poll SCM. Ask the Jenkins administrators which method your instance uses.
  6. Run it and check the result The build parameters are AGENT_NAME and RUN_EXTENDED_PIPELINE. Leave the second one off until Chapter 3 is in place.
Why this split is worth it. Developers get the security verdict within minutes of pushing, instead of waiting for deployments and performance tests that are not relevant to the change they just made.

5 Chapter 3 — Extended pipeline devSecOpsExtendedPipeline

When to choose this one

The second half of the flow, started after the security pipeline from Chapter 2. It deploys, runs the test suites, performs the dynamic security scan and then decides about the release and the promotion.

Eight stages: source checkout · deployment to the lower environment · regression tests · smoke tests · performance tests · AppScan DAST · Nexus release delivery · deployment to the higher environment.

Chapter 2 must be working first. This pipeline copies the archived config.yaml and the release decision from the security job. It inherits that verdict rather than deciding again, so a security finding that blocked the release there also blocks it here.

Steps

  1. Add a Jenkinsfile that names the upstream job
    Who: a developer on your team
    This is the one difference from the other chapters: securityPipeline must be the full Jenkins path of the job you created in Chapter 2. 
    @Library('DevSecOpsJenkinsLibrary') _

devSecOpsExtendedPipeline(
    projectNames:     'my-app',
    agentNames:       ['linux-agent'],
    securityPipeline: 'MyApp/MyApp-security-pipeline'
)
    Put this Jenkinsfile in the same repository as the security one. If you keep both in one repository, give this one a different file name such as Jenkinsfile.extended and point the job's Script Path at it.
  2. Complete the deployment and test sections of config.yaml
    Who: a developer on your team, with whoever owns the environments
    This pipeline needs the deploy, tests.smoke, tests.regression, tests.performance and dast blocks shown in Chapter 1. The config.yaml it actually uses is the one archived by the security job, so edit the file in the repository and let the security pipeline run once to publish it.
  3. Choose the deployment method
    Who: you, with the environment owners
    For virtual machines the library deploys over SSH by default. For OpenShift set deployTarget: openshift and provide the cluster tokens as credentials. Confirm with the environment owners which applies to your application, and that the deployment user and directory in the configuration are correct.
  4. Create the Jenkins job
    Who: you
    Create it as in Chapter 1 step 5, named to match what you put in securityPipeline, for example MyApp-extended-pipeline. Do not add a commit trigger — this job is started by the security pipeline or by a person.
  5. Add the Copy Artifact permission
    Who: the Jenkins administrators
    This job reads files archived by the security job. On some Jenkins instances that requires the upstream job to permit it. If the first run reports that it cannot copy artifacts, this is the setting to ask about.
  6. Connect the two jobs
    Who: you
    Go back to your security job's config.yaml and set jenkins.pipeline.extendedPipeline to this job's path. From then on, running the security pipeline with RUN_EXTENDED_PIPELINE ticked starts this one automatically.
  7. Run it and check the result The build parameters are AGENT_NAME and DEPLOY_HIGHER_ENV.

6 Chapter 4 — SAST scanning pipeline devSecOpsSASTScanningPipeline

When to choose this one

The smallest option: it checks out your code and runs the AppScan static security scan, nothing else. Use it when you want a security scan of the source without building, testing or deploying — typically on a weekly schedule, for an application whose main pipeline lives elsewhere, or as the very first step of onboarding.

Two stages: source checkout · AppScan SAST.

A good way to start. If you are onboarding a large application, running this pipeline first proves that the AppScan connection, the proxy and the certificates all work, before you invest time in the rest of the configuration.

Steps

  1. Add the Jenkinsfile
    Who: a developer on your team
    @Library('DevSecOpsJenkinsLibrary') _

devSecOpsSASTScanningPipeline(
    projectNames: 'my-app',
    agentNames:   ['linux-agent']
)
  2. Add a short config.yaml
    Who: a developer on your team
    This pipeline needs very little — only the AppScan identifiers and, if your source is not at the repository root, where to find it. 
    projects:
  my-app:
    appId:     "<AppScan application ID>"
    buildTool: gradle
    sourceDir: "."
    javaPath:  /usr/lib/jvm/java-17-openjdk

    asoc:
      url:   "https://bbh.cloud.appscan.com"
      keyId: "<AppScan key ID>"

    sast:
      scanName: "MyApp-SAST"
  3. Commit, push, and create the Jenkins job
    Who: you
    Create it as in Chapter 1 step 5, named for example MyApp-sast-pipeline. Its only parameter is AGENT_NAME.
  4. Put it on a schedule
    Who: you
    In the job configuration tick Build periodically and enter a schedule such as H 2 * * 1, which runs it once a week early on Monday morning. Scanning source code does not need to happen on every commit.
  5. Run it once by hand and check the result The report shows only the source checkout and the SAST stage, with a link to the AppScan report.

7 Part 4 — First run, verification and troubleshooting

7.1 What to look at after the first run

  1. Open the pipeline report On the build page choose Pipeline Report in the left menu. It shows every stage with its result, the finding counts against the policy, the coverage, and links to each tool's own report.
  2. Read the colours Green means the stage met the policy. Orange means it ran but broke a rule — the build is marked unstable and the release is blocked, but the pipeline carried on so you can see every problem at once. Red means the stage failed and the pipeline stopped there.
  3. Read the reasons Each orange or red stage carries the reason underneath it, naming the counts and the consequence. Fix what it names and run again.
  4. Check the Release policy card It lists every reason the release and the higher-environment deployment are blocked. When it is empty, your application is releasable.
A first run is rarely all green, and that is fine. The usual first-run findings are coverage below 60%, dependencies with known vulnerabilities, and test jobs that do not exist yet. Work through them one at a time — nothing has to be fixed before the pipeline is useful.

7.2 Common problems on a first run

What you seeWhat it means and what to do
config.yaml not found in workspaceThe file is missing from the repository root or is on a different branch than the one the job builds. Check the branch in the job configuration.
Project '...' not found in config.yamlThe name in projectNames in your Jenkinsfile does not match the key under projects: in config.yaml. They must be identical.
asoc.keyId must be setThe AppScan key ID from Part 2.3 is missing from config.yaml.
SAST fails while connecting, or times outThe agent cannot reach AppScan through the proxy. Raise it with the DevSecOps team quoting the agent label — the proxy account, the OIS certificate or the network route needs attention. Nothing in your configuration fixes this.
Nexus IQ reports the application does not existThe tools.nexusIq.application value does not match an application in Nexus IQ. Re-check it against Part 2.1.
Coverage shows not measuredThe build produced no coverage report. Confirm your test task generates JaCoCo XML, or point coverage.reportPath at it if it is in an unusual location.
DAST fails saying the HTML report could not be producedAppScan did not render the report in time or returned a message instead. The stage deliberately fails rather than recording zero findings. Re-run; if it repeats, ask the DevSecOps team to raise the report timeout.
A test stage is orange with NOT_CONFIGUREDA test job named in config.yaml does not exist in Jenkins yet. Create it, or leave it and accept the orange stage until the suite is ready.
No dependency-upgrade pull request appearsThe pipeline needs scm.bitbucket.url and a credential with write access. The report states this in plain language when it is the cause.

7.3 What happens from then on

  • Every run writes its metrics to InfluxDB, and the Grafana dashboards show the trend across runs — deployment frequency, lead time, change failure rate, recovery time, coverage and findings over time.
  • When Nexus IQ finds a vulnerable dependency, the pipeline prepares the upgrade, builds your application with it to make sure it still compiles, and only then opens a pull request for your team to review. It never merges anything.
  • The release and the higher-environment deployment stay blocked while any policy is broken, so the gate does its work without anyone having to remember it.
