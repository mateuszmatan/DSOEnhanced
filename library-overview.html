1 What the library is

A Jenkins shared library that gives an application a complete, opinionated DevSecOps pipeline: build, unit tests with a coverage gate, dependency and static security scanning, code quality analysis, artifact delivery, deployment to two environments, functional and performance testing, dynamic security scanning, and a single HTML report that explains the outcome.

An application adopts it with a Jenkinsfile of a few lines and one config.yaml. Everything else - the stage order, the thresholds, the report, the release rules - comes from the library, so every project that uses it is measured the same way.

One security policy for everyone

Severity thresholds and the required coverage live in the library, not in the project, so a team cannot loosen its own gate.

Nothing stops silently

Every stage runs on every build. A stage that breaks the policy turns orange and the build becomes unstable, but later stages still run so one report shows every problem at once.

Release is gated, not the pipeline

Findings above the policy do not abort the run; they block the release artifact and the higher-environment deployment.

Runs inside the script sandbox

No construct needs an administrator to approve a signature, so onboarding a project needs no script approval.

How findings are counted

The severity counts the pipeline reports are the ones printed in the tool's own report. For AppScan the library reads the Summary of security issues table of the downloaded HTML report, and falls back to counting the individual issue blocks only when a report carries no summary. The counts are verified a second time while the HTML report is written, against the report file archived with the build, so a report and a pipeline verdict can never disagree.

A missing report is a failure, not a clean result. If AppScan returns a message instead of a rendered report, the library recognises it, waits and retries until its timeout, and fails the stage rather than recording zero findings. A stage can only be green when a real report was parsed.

4 Code quality and coverage

  • Unit tests through the project's own Gradle, Maven or Flutter build; a failing test suite turns the stage orange and coverage is still measured on whatever reports were produced.
  • Line coverage read from JaCoCo (Gradle and Maven, with auto-detection of the report location) or from an LCOV file for Flutter, aggregated across modules and across projects.
  • Coverage gate against the minimum required by the library policy, shown in the report next to the measured value.
  • Per-class coverage printed to the console for the modules that were measured.
  • Test results published to Jenkins so the trend graphs and the failed-test list work as usual.

Flutter on SonarQube without a Dart plugin

SonarQube Community has no Dart or Flutter analyser, and the library does not need one. A Flutter project reaches SonarQube through the generic import formats every edition supports: the LCOV coverage file is converted to the Generic Coverage XML, and dart analyze findings are converted to Generic Issues, with ERROR mapped to a major bug, WARNING to a minor code smell and INFO to an informational one. The analysis runs on Linux, macOS and Windows agents. A team that does own the commercial sonar-flutter plugin can switch to its properties with one setting.

5 Policy engine and release gate

One policy, owned by the library

Maximum critical, high and medium findings per scanner and the minimum line coverage are defined in the library's own defaults.yaml. A project cannot raise them in its config.yaml, and every build logs the thresholds it was measured against.

Orange stages

A stage that breaks the policy is marked WARN, the build becomes UNSTABLE, and the reason names the finding counts and the consequence. The pipeline keeps going, so one run surfaces every problem instead of stopping at the first.

Release gate

The gate collects every verdict of the run and blocks the release artifact and the higher-environment deployment when a scanner count is above the policy, the coverage is below the minimum, or any stage is not green. The verdict is written to release-gate.json and archived, so a downstream pipeline inherits the decision of the upstream one instead of re-deciding it.

6 Automated dependency remediation (GoldenFix)

When Nexus IQ reports a policy violation the library can prepare the upgrade itself and open a pull request for review. It never merges anything.

What it changes

  • Only direct dependencies are touched. Transitive dependencies are left alone: they are upgraded by upgrading whatever pulls them in.
  • Manifests updated across the whole source tree, multi-module projects included: pom.xml (dependencies, dependencyManagement and the properties they reference, parent POMs too), build.gradle / build.gradle.kts and gradle.properties, package.json, requirements.txt, pubspec.yaml.
  • Anything it could not apply - a version managed by a BOM, for example - is listed in the pull request and in the report as not applied, with the reason.

Which version it picks

Two rules, in this order:

  1. Only the patch version may change. For x.y.z the major and the minor stay as they are, so 2.13.4 may become 2.13.5 but never 2.15.4. This keeps every proposed change backward compatible.
  2. Of those, the newest one without known vulnerabilities. The proposals are walked from the newest downwards and the first one Nexus IQ reports as free of violations wins. When none is clean, the one with the fewest known issues is taken.

A version Nexus IQ labels as its Golden Version still loses to a plain patch upgrade when it would move the minor. Only when no patch-level version is offered at all does the library fall back to the newest clean proposal of any level, and it says so in the pull request so a reviewer knows to check it by hand.

The pre-check build

The pull request is only opened if the application still builds with it. After applying the new versions in an isolated worktree the library builds the project. If the build fails it lowers every proposed version to the next lower one the supplier offers, reverts the worktree, applies again and rebuilds. Only a version set that builds is committed and proposed. If no offered version builds, no pull request is opened and the report says the upgrade needs a developer.

Every ecosystem whose manifest changed is verified, not only the project's main build tool, and each manifest is checked in its own directory, so a repository that mixes a pom.xml, an Angular package.json and a requirements.txt has all three checked.

Changed manifestDefault pre-check
pom.xmlmvn -B -q -DskipTests compile
build.gradle, build.gradle.kts, gradle.properties, *.versions.toml./gradlew --no-daemon --console=plain classes
package.jsonnpm ci --ignore-scripts, or npm install --ignore-scripts without a lock file
requirements*.txt, constraints*.txtpython3 -m pip install --dry-run -r <file>
pyproject.tomlpython3 -m pip install --dry-run .
pubspec.yamlflutter pub get

Each command is replaceable per ecosystem under goldenFix.verify.commands, for example to compile an Angular application rather than only resolving its dependencies. The attempt count and the timeout are configurable as well.

The pull request

  • Branch named GoldenFix-YYYYMMDDHHMM, pushed to Bitbucket, with a pull request that lists every change as a table of file, component, old and new version.
  • An existing pull request of the same run is updated rather than duplicated.
  • Reviewers can be set in the configuration.
  • The report explains the outcome in plain language, so a reader who does not work on the pipeline can act on it.

7 Build, test and delivery

Build tools

Gradle, Maven and Flutter, each with the project's own tasks, profiles and arguments taken from config.yaml. The wrapper is used when the repository ships one.

Functional and performance tests

  • Three independent job sets - smoke, regression and performance - each a list of Jenkins jobs.
  • Jobs run locally on the same Jenkins, or remotely on another Jenkins addressed by full URL with its own credentials.
  • Configurable parallelism, so a large job set does not saturate the controller.
  • Every job is reported with its status, duration and a link to its build; a job entry that is not configured yet is reported as such and counts as not successful.

Artifact delivery

  • Snapshot delivery after static analysis, release delivery only when the release gate allows it.
  • Maven artifacts deployed to a Nexus repository, with the version written back to the configuration.
  • Container images built and copied to Nexus for OpenShift projects.

9 Reporting and metrics

The HTML pipeline report

  • A stage flow grouped into phases, each stage with its result, duration, finding counts and links to the tool's own report.
  • A Security Gates table with the counts of every scanner against the policy, per project.
  • A release policy card listing every violation that blocks the release.
  • Coverage bars, SonarQube metric badges, the GoldenFix outcome and the full list of test jobs.
  • Multi-project aware: one report covers every project of the build, each with its own rows and boxes.
  • Written, archived and published even when the run failed; if the full report cannot be rendered a minimal one with the stage results is written instead.

Metrics

Stage results, durations, finding counts and coverage are pushed to InfluxDB, and the repository ships Grafana dashboards and queries built on them, so the trend across builds and across applications is visible outside Jenkins.

11 Prerequisites: Jenkins

Installation-specific global steps

The library calls four steps that are not public plugins and must exist as global variables in the Jenkins instance: reportBuild, reportUnitTest, reportSurefireTest and addSonarBadgesToDescription. Without them the Nexus delivery and SonarQube stages fail. Provide them, or remove the calls when porting the library to another Jenkins.

Script security

Nothing needs approval under In-process Script Approval. The library is written to stay inside the script sandbox, and its test suite loads every class and runs every pipeline under the real sandbox before a release.

13 Prerequisites: the application repository

A Jenkinsfile

@Library('DevSecOpsJenkinsLibrary') _

devSecOpsPipeline(
    projectNames: 'my-app',
    agentNames:   ['linux-agent']
)

A config.yaml in the repository root

One projects: section per project built by the job. A run fails early and says what is missing, so a first build is a fast way to validate the file. The minimum is:

projects:
  my-app:
    buildTool:  gradle            # gradle | maven | flutter
    appId:      "<HCL AppScan application id>"
    asoc:
      keyId:    "<HCL AppScan key id>"
    build:
      tasks:    ["clean", "build"]
    tests:
      unitTests:
        tasks:  ["test"]
    tools:
      sonar:
        projectKey: "<SonarQube project key>"
      nexusIq:
        iqApplication: "<Nexus IQ public id>"

Add the sections for the capabilities the project uses: dast (target URL and presence), scm.bitbucket (for GoldenFix pull requests), goldenFix, tests.smoke / regression / performance, deploy.vm or the OpenShift settings, and coverage.reportPath when the coverage report is not in a standard location. The template in the repository lists every option with its default.

The build itself

  • A build that runs unattended on an agent, with no interactive prompt.
  • A unit test task, and a coverage report: JaCoCo XML for Gradle and Maven, or an LCOV file for Flutter. Without a coverage report the stage turns orange, because the required coverage cannot be verified.
  • Direct dependencies declared in a manifest the library can edit, if GoldenFix should be able to propose upgrades.
  • A deployable artifact or a Dockerfile, if the delivery and deployment stages are used.

What the pipeline needs from the environment

  • A deployed, reachable instance of the application for DAST and for the functional tests.
  • Jenkins jobs for smoke, regression and performance tests, created before the pipeline reaches those stages; an entry with an empty job name is reported as not configured and turns the stage orange.

14 Onboarding checklist

  1. Register the library in Jenkins and install the plugins of section 11.
  2. Register the SonarQube and Nexus IQ servers, and add the credentials.
  3. Create the application in Nexus IQ, HCL AppScan and SonarQube, and note the three identifiers.
  4. Add the Jenkinsfile and config.yaml to the repository.
  5. Make sure the build produces a coverage report, and point coverage.reportPath at it if it is in an unusual place.
  6. Run the job once. The first run validates the configuration, logs the thresholds it measures against and writes the report even if stages fail.
  7. Read the report, fix what it names, and only then wire in the deployment, the test job sets and the GoldenFix pull requests.
The pipeline is designed to be onboarded incrementally. A project can start with build, unit tests and the three static scans, and add deployment, functional tests and DAST later; the stages it does not configure report themselves as not required or not configured instead of breaking the run.
